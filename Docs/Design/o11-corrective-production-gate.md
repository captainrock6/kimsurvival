# O11 교정·프로덕션 후보 완료 게이트

O11의 목적은 O10-H1에서 확인된 `P0 2건`과 `P1 5건`을 모두 닫고, 임시 화면을 더 오래 시험하는 대신 채택된 스타일과 실제 게임 자산이 연결된 다음 인간 후보를 만드는 것이다. O10 후보 `aa2bb218`은 재사용하지 않는다.

## 병렬 작업과 소유권

| 작업 | 소유 범위 | 완료 산출물 |
|---|---|---|
| Unity 시스템 | 다층 일반 설비 배치·저장, 출항 transaction, 증축 후 상태 복귀, 뗏목 준비 부담 | `codex/o11-system-core` 제품 커밋과 단위/Play 검증 |
| 아트·UI | 채택 V2 기반 엔진 UI, 7지역 수색 표현, 김씨 핵심 애니메이션과 런타임 연결 | `codex/o11-production-visuals` 제품/자산 커밋과 실제 Game View 캡처 |
| 기획·밸런스 | 기력 소모·회복 표, 연속 수색 pacing, 세 탈출 경로 상대 부담 | `codex/o11-survival-balance` 수치 계약·제품 데이터와 시뮬레이션 |
| QA | 일곱 결함 red-first 계약, KO/EN 레이아웃, Unity edit/play/render/build 게이트 | `codex/o11-qa-gate` 독립 러너와 RED→GREEN 증거 |

각 작업은 `aa67a12b`에서 시작한다. 다른 작업의 소유 파일을 수정하지 않으며, 디렉터 작업만 브랜치를 통합하고 Forge 원장·후보 빌드·최종 보고서를 갱신한다.

| `O10-H1-P0-001` | 작업대·빗물받이·침대·소파 등 일반 설비를 완공된 시작층·2층·지하에서 배치·재배치한다. `StableRoomId + 방 내부 좌표`가 저장·복원되며 출입구·사다리·통로·충돌 배치는 거부한다. 모닥불·탈출 설비·연결부만 고정 앵커다. |

## 아트 채택 경계

- 채택된 V2는 스타일과 엔진 UI 구현의 기준이다.
- 기존 `engine_ready` 자산과 채택 캐릭터 부품을 재배치·애니메이션화한 엔진 자산은 O11에 사용할 수 있다.
- 새로 생성한 미채택 raster 결과는 `review`로 남기고 O11 필수 런타임에 연결하지 않는다. 같은 역할의 채택/엔진 자산이 없으면 O11 빌드를 만들기 전에 사용자 채택 판단이 필요하다.
- 합성 스타일 벤치마크 한 장을 전체 화면 배경이나 UI로 사용하지 않는다.

## 통합 순서

1. QA red-first 러너를 먼저 통합하고 기존 O10 상태에서 예상 RED를 고정한다.
2. 밸런스 데이터·계약을 통합한다.
3. 시스템 제품 변경을 통합해 P0와 상태/뗏목 계약을 GREEN으로 만든다.
4. production visuals를 통합하고 실제 Game View에서 가독성·애니메이션을 검증한다.
5. Unity 컴파일, O11 Edit/Play, KO/EN 1280×800·1920×1080 render capture, Windows x64 `BuildOptions.None`, 플레이어 스모크를 순서대로 수행한다.

## O11 후보 생성 조건

- 위 일곱 항목이 모두 자동 검증 `PASS`이고, P0는 실패·중복·저장복원 경로까지 통과한다.
- 컴파일 오류·경고 `0/0`을 목표로 하며 새 관리 코드 예외·크래시가 없다.
- 필수 아트가 `engine_ready`, 기존 채택 자산 기반 Unity 산출물, 또는 명시적으로 채택된 결과다.
- 실제 캡처를 사람이 확인해 가방·팝업·목표·김씨·수색물이 서로 겹치지 않는다.
- Release EXE·Data 폴더·ZIP과 SHA-256, 소스 커밋, Player 로그를 기록한다.
- 이 조건 전에는 30분 자연 플레이를 재개하지 않는다. 합격 후 새 세션 이름은 `O11-H1`이다.

물리 게임패드는 최종 제출 후보의 별도 인간 게이트로 유지한다. O11 후보에서는 키보드·마우스와 synthetic gamepad 회귀를 수행하되 물리 장치 검증을 거짓으로 PASS 처리하지 않는다.
